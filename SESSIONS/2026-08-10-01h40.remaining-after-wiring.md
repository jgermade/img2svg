## Three things this session decided that the plan had wrong

Same pattern as last time: all three surfaced while writing the comment that
justified them.

**`canvas` is a field of `Conversion`, not a member of `Detail::Cluster`.** The
plan put the canvas size inside the cluster variant, next to `grid` inside the
grid variant. They are the same number — what goes in the `viewBox` — so
duplicating it under two names would make the CLI, the page and the snapshot
headers ask which mode a conversion came from before reading a value that means
the same thing either way. Hoisting it also kept `gridWidth` in `wasm.rs` reading
a plain field, so the existing `.d.ts` did not change at all.

**`--min-thickness 1` already eats one-pixel lines.** The previous note said
raising it past 1 starts costing real detail. Writing the help text made the
arithmetic explicit: thickness is `2·area/perimeter`, a 1×L band is
`2L/(2L+2) < 1` for every L, and the test is `< min_thickness`. So the default
removes *every* one-pixel-wide feature, hairline artwork included. That is still
the right default for a photo — fringes outnumber real hairlines by orders of
magnitude — but it is a trade, not a free win, and it now says so in the CLI
help, in `ClusterOptions`, in `docs/cli.md` and in the web panel. `tests/photo.rs`
pins both sides of it.

**One wasm bundle, not two.** The rule was "under ~50 KB of growth keep one
bundle". Measured: 152 → 209 KB raw, but 52 → 68 KB brotli and 63 → 84 KB gzip.
The rule's baseline was written in raw bytes, so by its own units it says split;
by the units that are actually downloaded it is 17 KB. Seventeen kilobytes does
not pay for two `pkg/` directories, a loader that chooses, two wasm builds in CI
and two `.d.ts` files to watch. CI now builds `--features wasm,photo`. Revisit if
the curve fitters move that number.

## 1. Phase 4: the fitters

What the IR guarantees, and what a fitter may therefore assume:

- Every boundary appears **once**, as a half-edge with a region on each side. Fit
  it, and both faces reference the same geometry — one forward, one reversed.
  There is no seam to hide and no stacking needed.
- `points` is the **dense** polyline, one point per lattice corner.
- A chain that closes on itself **repeats its first point at the end**. That is
  the signal to fit it as periodic instead of leaving two loose ends.
- A chain's endpoints are nodes, shared with every chain continuing past them.

### `polygon`

Ramer–Douglas–Peucker per half-edge, tolerance in pixels. RDP keeps the endpoints
fixed, which is exactly what is needed: the nodes must not move, or the chains
meeting there come apart. Nearly free, and the right answer for flat-shaded art.

It is also the cheapest visible win available: `photo` output today is a
staircase at three to four times the path data it needs.

### `spline`

Corner detection over a turning-angle window, tangent estimation, least-squares
cubic fit with recursive subdivision at the worst point (Schneider). Roughly
potrace's pipeline, and the part with real mathematics.

Three details that are easy to miss:

- **`path_data` only knows `h`/`v`** (`svg.rs`) and needs a curve-aware sibling
  emitting `C`. `path_precision` and coordinate quantisation belong here too.
- **`shape-rendering="crispEdges"` is hardcoded in the `<svg>` element**
  (`svg.rs`). Right for a pixel staircase on integer coordinates, wrong for
  curves — it will alias every Bézier. It has to become conditional on the fit.
- **Tangent continuity across a node is not guaranteed.** Each chain is fitted
  independently, so two chains meeting at a node agree on the point but not the
  direction. For a three-region junction that is correct: it is a real corner.
  Where it will show is a node that is geometrically smooth. The fix, if it turns
  out to matter, is to estimate the tangent at shared nodes once and hand it to
  both chains as a constraint.

And the reason the whole two-axis shape exists: **`grid` + `spline`** —
vectorising a sprite with smooth curves *after* recovering the grid, so the
curves follow the art pixels instead of the upscaling artefacts.

### What phase 4 touches on each surface

`Fit` gains variants, so: `--fit` on both CLI subcommands (it is shared, it goes
in `Common`), a `fit` key in both wasm readers, and a control in both web panels.
The photo panel already has the note saying the contours are still staircases —
that note is what comes out when the fitter lands.

## 2. Leftovers not tied to a phase

- **Real progress on the page.** The photo path is loops over rows and regions,
  so it can report actual progress through a callback instead of the
  indeterminate bar. At 163 ms on a label it is not urgent; on a 4 Mpx photo at
  ~500 ms it is.
- **Corpus in CI.** Still not reachable from a clean clone; `REQUIRE_CORPUS=1` is
  wired and waiting. Release asset, fixtures repo, or LFS.
- **`.d.ts` guard.** Nothing catches a breaking change to the JS API, and photo
  mode just added a second result type to it. Build the wasm in CI and diff
  `web/pkg/img2svg.d.ts` against a committed copy.
- **`checker.rs` has no golden from a clean clone**, same corpus reason.
- **Homebrew Rust shadows rustup locally** — `wasm32-unknown-unknown` is only
  installed under rustup, so anything touching the web build needs
  `PATH="$HOME/.cargo/bin:$PATH"` until this is fixed on the machine.
- **The look-at-it loop still is not in the repo.** It got rebuilt again this
  session, twice: headless Chrome screenshotting the snapshot SVGs side by side
  (which is how the fixture was confirmed to exercise what it claims), and a
  CDP driver that loads the page, drops a file in, waits for the *real*
  conversion and reads back the stats line (`--virtual-time-budget` fast-forwards
  past the wasm and screenshots an empty pane). The second one is what verified
  the web wiring end to end. Worth keeping, and it must stay out of CI: it needs
  Chrome and it answers questions no assertion can.

## What keeps being true

- **The eleven pixel-art snapshots do not move.** They have now survived the
  rename, phase 1, the colour work, the half-edge convention change, the whole
  photo pipeline, and the `Conversion` refactor that moved three of the fields
  the snapshot header prints.
- **Fewer colours is not fewer regions.** Held for the tolerance sweep, for
  `max_colors`, and again for `gradient_step` in `tests/photo.rs` — which is why
  that test asserts on colours and deliberately asserts nothing about regions.
- **Measure, then look.** The region counts found the first kind of speck; the
  eye found the fringe bands. This session the numbers said the fixture was
  fine and looking at it confirmed the one-pixel line was the thing being
  filtered, not something the palette had absorbed.
- **The plan's specifics keep being wrong in the same way, and writing down *why*
  keeps catching them.** Six for six now.
