## The thing this session found that the plan had wrong

Seventh in a row, and the same shape as the other six: it surfaced while looking
at the code that would have to change.

**The fit happens per ring today, and it has to happen per half-edge.**
`svg::render` calls `fit::ring_data`, which concatenates the ring's points with
`Regions::ring_points` and simplifies the whole closed sequence
([svg.rs:59](../src/svg.rs#L59), [fit.rs:19](../src/fit.rs#L19)). With `Pixel` on
integer coordinates that is invisible — collapsing collinear runs across a node
gives the same staircase — so nothing has caught it.

RDP over a whole assembled ring would not be invisible. It simplifies *through*
the bifurcations: a node where three regions meet is just another interior vertex
to it, and the first thing it does is drop the ones that look straight. The two
faces of a shared boundary would then be simplified inside two different rings,
with different neighbours on either side of the node, and come out disagreeing —
which is precisely the hairline the half-edge IR was built to make impossible.
The IR keeps its promise and the fitting stage throws it away at the last step.

So the shape is: **fit each `EdgeId` once, then assemble rings from fitted
edges**, reversing where the ring says `reversed`. It is the same information
flow the IR already describes, moved one stage later than it is today. Worth
doing under `polygon`, where it can be checked against a fitter whose output is
easy to reason about, rather than discovering it under `spline`.

## 1. `Fit::Polygon`

Ramer–Douglas–Peucker per half-edge, tolerance in pixels. RDP keeps the endpoints
fixed, which is exactly the requirement: nodes must not move, or the chains
meeting there come apart.

It stays in integers. RDP only *selects* vertices from the polyline it is given,
and those are lattice corners, so nothing new is invented and `Point` does not
change. Floats, `path_precision` and coordinate quantisation belong to `spline`.

It is also the cheapest visible win left: `photo` output today is a staircase at
three to four times the path data it needs.

What it touches on each surface: `--fit` in `Common` — it is shared, so it lands
on both subcommands at once ([cli.rs:38](../src/cli.rs#L38)) — a `fit` key in both
wasm readers, and a control in both web panels. The default stays `Pixel`, so the
eleven pixel-art snapshots do not move; the new snapshots go in `tests/photo.rs`.

## 2. `Fit::Spline`

Corner detection over a turning-angle window, tangent estimation, least-squares
cubic fit with recursive subdivision at the worst point (Schneider). Roughly
potrace's pipeline, and the part with real mathematics. Three details carried
forward from the previous note, all still true:

- **`path_data` only knows `h`/`v`** and needs a curve-aware sibling emitting
  `C`.
- **`shape-rendering="crispEdges"` is hardcoded in the `<svg>` element**
  ([svg.rs:97](../src/svg.rs#L97)). Right for a staircase on integer coordinates,
  and it will alias every Bézier. It has to become conditional on the fit.
- **Tangent continuity across a node is not guaranteed.** Correct at a
  three-region junction, which is a real corner; visible at a node that is
  geometrically smooth. The fix, if it turns out to matter, is to estimate the
  tangent at shared nodes once and hand it to both chains as a constraint.

And the reason the whole two-axis shape exists: **`grid` + `spline`** —
vectorising a sprite with smooth curves *after* recovering the grid, so the curves
follow the art pixels instead of the upscaling artefacts.

## 3. Leftovers not tied to a phase

- **`.d.ts` guard.** The cheapest thing on this list and almost already there: CI
  builds the wasm, so it only needs a committed copy of `web/pkg/img2svg.d.ts` and
  a `git diff --exit-code` against it. Ten lines, and the JS API stops being able
  to break in silence — photo mode just added a second result type to it.
- **Real progress on the page.** The photo path is loops over rows and regions, so
  it can report actual progress through a callback instead of the indeterminate
  bar. At 163 ms on a label it is not urgent; on a 4 Mpx photo at ~500 ms it is.
- **Homebrew Rust shadows rustup locally** — `wasm32-unknown-unknown` is only
  installed under rustup, so anything touching the web build needs
  `PATH="$HOME/.cargo/bin:$PATH"` until this is fixed on the machine.
- **The look-at-it loop still is not in the repo.** Headless Chrome screenshotting
  the snapshot SVGs side by side, and a CDP driver that loads the page, drops a
  file in, waits for the *real* conversion and reads back the stats line
  (`--virtual-time-budget` fast-forwards past the wasm and screenshots an empty
  pane). It has now been rebuilt three times. It must stay out of CI — it needs
  Chrome and it answers questions no assertion can — but it should stop being
  rebuilt from memory.

## What keeps being true

- **The eleven pixel-art snapshots do not move.** They have now survived the
  rename, phase 1, the colour work, the half-edge convention change, the whole
  photo pipeline, and the `Conversion` refactor.
- **Fewer colours is not fewer regions.** Held for the tolerance sweep, for
  `max_colors`, and again for `gradient_step`.
- **Measure, then look.** The region counts found the first kind of speck; the eye
  found the fringe bands.
- **A guarantee is only kept if the last stage keeps it too.** The IR extracts
  every boundary once and both its faces, and the fitting stage was going to undo
  that by simplifying assembled rings. New this session, and the general form of
  it is worth watching for.
- **The plan's specifics keep being wrong in the same way, and writing down *why*
  keeps catching them.** Seven for seven now.
