## What the plan had wrong, again before any code

Both open items were described in earlier notes, and looking at the code that
implements them moved one of them somewhere else entirely.

### Node tangents are not the continuity problem. The nodeless loop is.

Three notes in a row have carried this line: *"tangent continuity across a node
is not guaranteed — correct at a three-region junction, visible at a node that is
geometrically smooth"*, with the fix being to estimate the tangent once per node
and constrain both chains.

But a node is not an arbitrary split point.
[`boundary.rs:26`](../src/boundary.rs#L26) defines it: corners of the pixel
lattice have degree 0, 2, 3 or 4, and **only degree 3 and 4 are nodes** — three
or four regions meeting. That is a genuine corner essentially every time. The
"node that is geometrically smooth" needs a third region kissing a smooth
boundary at exactly one lattice corner. It exists, it is rare, and what it costs
is a slight kink — not a hairline, because both faces of each chain still agree.

Meanwhile, two lines further down ([`boundary.rs:183`](../src/boundary.rs#L183)),
sits the thing nobody wrote down:

> Después lo que quede son bucles que no pasan por ningún nodo —una región suelta
> sobre un fondo uniforme no tiene por dónde bifurcarse— **y se parten por donde
> caiga**.

A region floating on a uniform background is a closed chain with no node at all,
split at whatever corner the sweep reached first. That is an arbitrary point on
what is typically the *smoothest* contour in the picture. Pin a corner there and
every floating blob in every photo gets one kink, in a different place each time
the segmentation shifts by a pixel.

So the fix is not shared node tangents. It is that **a closed chain is fitted as
periodic**: detect corners with wraparound, and if the seam is not a corner,
estimate its tangent from the points on *both* sides of it, so the curve leaves
in the same direction it arrives. Same cost, and it fixes the case that actually
occurs on every input.

The node case gets the honest treatment instead: endpoints of an open chain are
pinned as corners, because they are junctions of three or more regions, and the
rare smooth-junction kink is accepted and written down.

### The writer needs rounded absolutes, not rounded deltas

`path_data` emits integers today. Curves need decimals, and the commands are
relative, so rounding each delta as it is written makes the error accumulate
along the path — a contour of two thousand segments would drift visibly from its
own start. Coordinates get rounded **absolutely**, once, and the deltas are then
computed between already-rounded positions. Both faces of a boundary round the
same absolute values, so the seam survives rounding, which it would not if each
face accumulated its own drift.

## 1. `Fit::Spline`

**The representation has to carry curves.** `Fitted(Vec<Vec<Point>>)` becomes a
vector of `Vertex { p: (f64, f64), cin: Option<Pt>, cout: Option<Pt> }` — the
control point arriving at `p` and the one leaving it. A cubic between two
vertices uses the first's `cout` and the second's `cin`; both absent is a
straight line.

Reversing a chain reverses the vector and swaps `cin`/`cout` in each vertex. That
is exact — the same four control points in the other order — so the two faces of
a shared boundary still get identical geometry, which is the whole point of the
IR.

**`region::chain` stays the only place that knows the repeat-point rule.** It
becomes generic over a small `Reversible` trait (identity for `Point`, the
cin/cout swap for `Vertex`). The previous session merged two copies of that rule
into one function precisely because having it twice is how it goes wrong;
adding a second assembler for curves would put it straight back.

**The maths**, per chain:

- **Corners** over a turning window: compare the chord `k` points back with the
  chord `k` points forward; a turn past the threshold is a corner. On a lattice
  this reads a 90° rectangle corner as 90° and a 45° staircase as ~0°, which is
  the distinction that matters. Window and threshold stay **constants**, not
  knobs: `--fit spline` reuses `--fit-tolerance` and adds no new option to any of
  the three surfaces.
- **Tangents** from a short averaged chord rather than the single neighbouring
  lattice step, which is axis-aligned and therefore noise.
- **Schneider**: chord-length parameterisation, least squares with the end
  tangents fixed, Newton–Raphson reparameterisation, and split at the worst point
  when the error is still over tolerance.
- **A straight run emits `l`, not `C`.** Smaller, and it keeps the canvas border
  as line segments, which is what lets the seam test keep its existing
  border rule.

**The snapshots must not move.** Fifteen of them, and `Pixel` stays the default.
Integral coordinates have to format byte for byte as they do today — including
`-0`, which the float writer will produce and the integer writer never did.

## 2. Real progress

**A callback, not a field in `Config`.** `Config` is `Clone + Debug + Default`
and is passed around everywhere; putting a `&dyn Fn` in it would infect all of
that with a lifetime. Instead a second entry point takes the callback and
`convert_rgba` delegates to it with a no-op.

Stages: palette, regions, boundaries, fitting, document. The overall fraction
needs weights, and those get **measured on a corpus photo** rather than guessed —
that is the one number in this that can be wrong quietly.

Calls get throttled to whole percents in Rust, so the page cannot be flooded with
a JS call per pixel row and no caller has to remember to throttle.

Then `onProgress` in the options of both wasm entry points, a message from the
worker, and `app.js` replaces the pulsing indeterminate bar
([`app.js:151`](../web/app.js#L151)) with the real one during `convert`.

## What landed

**`Fit::Spline`,** on all three surfaces. Schneider: corners by turning angle
over a four-pixel window, chord-length parameterisation, least squares with the
end tangents fixed, Newton reparameterisation, subdivision at the worst point.
Straight runs come out as lines. The representation changed underneath —
`Fitted` now holds vertices carrying the control point arriving at each and the
one leaving it — and `region::chain` became generic over a `Chainable` trait so
the repeat-point rule still lives in exactly one place.

**Real progress,** measured rather than guessed. `convert_rgba_with` takes a
callback; `Config` was left alone on purpose, since putting a `&mut dyn FnMut`
in a `Clone + Debug + Default` struct that gets copied everywhere would infect
all of it with a lifetime. Throttled to whole percents inside `Progress`, so no
caller has to remember to.

The fifteen snapshots did not move. The representation change was landed on its
own first, with a stub fitter, precisely so they could prove that.

## What the plan had wrong

Eleventh in a row, and three this time.

**1. The spline is not a compression feature — and every note so far implied it
was.** The polygon's ordering ("the cheapest visible win left") set the
expectation, and the measurement kills it: against the polygon *at the same
tolerance*, the spline is bigger on every input tried.

| | polygon | spline |
| --- | --- | --- |
| corpus photo, tol 1.5 | 84.6 KB | 103 KB |
| corpus sprite via `pixelart`, tol 1.5 | 16.8 KB | 18.7 KB |
| three flat overlapping discs, tol 1.5 | 1,033 B | 1,281 B |

It is arithmetic, not a bug: a cubic costs six numbers where a line costs two,
and it does not replace six lines. Even the case built to favour it — flat
discs, genuinely curved, shared boundaries — loses. What it actually buys is that
the outline stays smooth at any zoom, where a polygon's facets are frozen into
the file. That is a real reason to want it and a completely different one, and
the docs now say so instead of implying a smaller file.

Worth adding, because it is the number a user will see: at their *own* defaults
the two land together (105.6 KB against 103.2 KB). That is the larger tolerance
paying for the extra numbers, not the curves being cheap.

**2. The fitters cannot share a default tolerance.** The session started by
merging `POLYGON_TOLERANCE` into one `TOLERANCE` on the grounds that both promise
the same thing. They do promise the same thing, and they still need different
numbers, which took a sweep to see: at 0.75 the spline **degenerates**, emitting
2 curves and 108 lines for a circle that it draws in 8 segments at 1.5.

| tolerance | segments | SVG |
| --- | --- | --- |
| 0.75 | 2 curves + 108 lines | 618 B |
| 1.0 | 6 + 36 | 472 B |
| 1.25 | 14 + 12 | 568 B |
| **1.5** | **4 + 4** | **290 B** |
| 3.0 | 4 + 4 | 290 B |

The reason is a floor nobody had written down: **the contour is a staircase, so
it arrives with 0.707 px of quantisation error already in it.** The polygon never
notices — its vertices *are* lattice corners, which is why it honours tolerance 0
exactly — but a curve has to pass near all those steps at once, and below 1.0 it
spends the whole budget chasing them. So `--fit-tolerance` lost its fixed default
and takes the one belonging to the fitter named; the page resets the slider on
switch, because carrying 0.75 over to the spline is precisely the value that
makes it look broken.

**3. Node tangents were the wrong worry; the nodeless loop was the right one.**
Predicted before writing code, from `boundary.rs`: a node is a lattice corner
where three or four regions meet, so it is a genuine corner nearly always. The
case that actually bites is a closed loop that passes through no node — an
isolated region on a uniform background — which gets split *wherever the sweep
reached it first*. Treat that as a corner and every floating blob gets a kink in
an arbitrary place. Closed chains are therefore fitted as periodic, with the seam
tangent estimated from both sides.

## Verified rather than assumed

Two new tests, both made to fail first, and **both were vacuous when first
written** — which is its own lesson.

- `un_circulo_sale_liso` measures the turn at every joint of a digitised circle.
  Written to check only curve-to-curve joints, it passed with the seam handling
  deliberately broken: a digitised circle has flat runs at its four cardinal
  points, so *every* joint is curve-to-line and the loop body never ran. Checking
  all joints: **0.00 as it stands, 0.60 with the seam treated as a corner.**
- `las_dos_caras_de_una_frontera_curva_se_ajustan_igual` extends the seam check
  to compare whole cubics, controls included — two curves sharing endpoints can
  still bulge apart. The first version reused the existing nine-pixel fixture,
  which is too small to produce a single curve, and passed with reversal broken.
  With two overlapping discs it fails as it should: `la curva [...] la dibujan 1
  caras, no dos`. It now asserts there *are* curves before believing itself.

The line fallback also went through a wrong turn worth recording: the spline was
emitting 40% more segments than the polygon on the same contours, and the fix
tried first — re-simplifying runs of lines with RDP — changed the total by 12
bytes. The measurement that explained it was the segmentation, not the fitter:
4,128 chains averaging 16 points, 1,710 of them 6 points or fewer. On banded
photo output there is simply nothing long enough to curve. The RDP pass stayed
anyway (it is the same code path as the polygon now, which is where the
unification of `rdp_keep` came from), but it is not what mattered.

Progress weights are measured too: of 471 ms on a 2730×1536 corpus image, 148
palette, 172 labelling, 46 specks, 79 boundaries, 26 document. Stable across
image size and across fitter — with curves the document stage is still 6%, which
says the fitting is not where the time goes.

`scripts/web-smoke.mjs` gained checks for both: that `fit: "spline"` emits `c`
commands, and that `onProgress` is called, monotonic, ends at exactly 1, and
never more than once per percent (70 calls on the test buffer).
