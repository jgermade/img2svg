# img2svg: segmentation × fitting

**2026-08-09** — Plan for extending `px2svg` to general raster images (not pixel
art) without changing any current behaviour.

---

## 1. The decision

Turn the binary into `img2svg` with **two orthogonal axes**, not two sibling
programs. This is VTracer's decomposition (four pluggable stages: segmentation,
curve fitting, color fitting, output optimization) with better CLI ergonomics.

| Segmentation (image → regions) | Fitting (contour → path) |
| --- | --- |
| `grid` — grid + checkerboard + discrete palette (what we have today) | `pixel` — literal staircase, `h`/`v` commands |
| `cluster` — color clustering for photos | `polygon` — RDP over the loops |
| `binary` — later | `spline` — cubic Béziers |

**Why two axes and not two sibling subcommands.** This project's pixel-art mode
is not VTracer's `--mode pixel`. Theirs traces pixel borders on the
full-resolution image; ours detects period and phase and **reduces to one logical
pixel per cell** (`grid.rs:278`), with the `viewBox` in art pixels. That is an
interpretation of the *input*, not an output primitive.

The practical consequence: **`grid` + `spline` is a feature nobody else has** —
vectorizing a sprite with smooth curves *after* recovering the grid, so the
curves follow the art pixels rather than the upscaling artifacts. With `pixelart`
and `curves` as sibling subcommands that combination would be inexpressible.

### CLI shape

Subcommand = segmentation. Flag = fitting.

```
img2svg pixelart  [--fit pixel|polygon|spline]   # default: pixel
img2svg photo     [--fit pixel|polygon|spline]   # default: spline
```

- The segmentation options genuinely *are* disjoint (`--scale` / `--offset` /
  `--keep-checkerboard` versus `--filter-speckle` / `--color-precision` /
  `--gradient-step`), so each subcommand keeps a clean `--help`. VTracer has both
  axes as flat flags, which is why their help reads badly.
- Shared options (`-o/--output`, `-q/--quiet`, `-b/--background`, `--fit`,
  `--simplify`, `--path-precision`) go in a struct with `#[command(flatten)]`.
- Different defaults per subcommand ⇒ VTracer's presets (`bw`, `poster`, `photo`)
  come for free.
- **Keep `px2svg`** as a second five-line `[[bin]]` that forwards to
  `img2svg pixelart`. That preserves the README, the GitHub Action and every
  existing invocation. Cleaner than making the subcommand optional via
  `args_conflicts_with_subcommands`, which produces terrible user-facing errors.
- Later: **`img2svg auto`**. The detector already exists — `grid::detect`
  returning `cell > 1` above `MIN_SCORE` (`grid.rs:74`) *is* a pixel-art
  classifier with a confidence measure. Neither VTracer nor potrace picks a mode
  on its own.

### Library shape

```rust
pub enum Segmentation { Grid(GridOptions), Cluster(ClusterOptions) }
pub enum Fit { Pixel, Polygon { tolerance: f64 }, Spline { corner: f64, /* … */ } }

pub struct Config {
    pub segmentation: Segmentation,
    pub fit: Fit,
    // shared: background, path_precision, grouping…
}
```

Pipeline: `image → segment → Vec<Region> → fit → svg`.

`convert()`, `convert_rgba()` and `convert_image()` **keep their exact current
signatures** as wrappers over `Grid + Pixel`.

## 2. What VTracer has already solved

Every one of their parameters is the scar of a real problem. Worth reading as a
list of what is coming for us:

| Problem | Their solution |
| --- | --- |
| **Seams between adjacent regions** | `--hierarchical stacked` (default) vs `cutout` |
| Speckle explosion on photos | `--filter-speckle` 0..=128 px |
| Too many colors | `--color-precision` (bits per channel), `--max-colors`, `--palette` |
| Gradients that cannot be represented | `--gradient-step` 0..=255: deliberately bands them |
| Over/under-fitting of curves | `--mode pixel\|polygon\|spline` + `--simplify <tol>` |
| File size | `--path-precision`, `--optimize 0\|1\|2` |
| Uneven lighting in B/W | `--adaptive` (Bradley–Roth), `--adaptive-window`, `--adaptive-t` |
| Nobody knows what to put in 15 knobs | `--preset bw\|poster\|photo` |

### The seam problem deserves its own note

If every region is emitted as an independent closed polygon and two of them share
a border, the renderer antialiases both sides and a hairline of background shows
through. With curves it is worse: **the shared border gets fitted twice with
different results** and the gap stops being a hairline. That is why VTracer's
default is `stacked` (layered shapes, the top one covers the joint), why they
admit `cutout` still has seams, and why their `--simplify` is seam-free — it
simplifies each shared boundary **once for both faces**.

We do not have this problem today: integer coordinates and
`shape-rendering="crispEdges"` (`svg.rs:135`). **We inherit it the day we emit
curves.**

→ Decision to make **when defining the IR, not afterwards**: if `Region` carries
independent loops, every boundary is fitted twice. If it carries half-edges with
both adjacent regions, it is fitted once and the problem does not exist.

### Where we beat them

VTracer does no grid detection. `grid.rs` and `checker.rs` have no equivalent
there. The merged result is a strict superset of VTracer for pixel art.

## 3. Phases

### Phase 0 — Safety net (§4). Before touching anything.

### Phase 1 — Refactor to two axes, no behaviour change

- Introduce `Segmentation` / `Fit` and the `Region` IR.
- Move `simplify()` out of `trace()` (`trace.rs:81-83`) and make it the `pixel`
  fitter's own step. The `polygon` and `spline` fitters want the dense polyline,
  not the already-collapsed one.
- `convert*()` keep their signatures. The phase 0 tests must stay green
  **without being regenerated**.

### Phase 2 — CLI rename

- `[[bin]] img2svg` with `pixelart` / `photo` subcommands.
- `[[bin]] px2svg` as a forwarding alias.
- Update README and `.github/workflows/pages.yml`.

### Phase 3 — `cluster` segmentation

- Run-based clustering (not per-pixel flood fill: it does not scale on photos).
- `filter_speckle`, `color_precision`, `gradient_step`, fixed palette.
- Extend `background.rs` with a tolerance — today it compares exact colors
  (`background.rs:26`).

### Phase 4 — `polygon` and `spline` fitters

- `polygon`: RDP. Nearly free, the loops are already there.
- `spline`: corner detection plus least-squares fitting with recursive
  subdivision. This is the part with real mathematics (~400 lines).
- Resolve the seams here, according to what was decided in the IR.

### Phase 5 — Web sub-apps

The page inherits the same decomposition: **sub-app = segmentation**, with the
fitting selector as a shared control present in both. `img2svg pixelart --fit
spline` becomes a "smooth" dropdown inside the pixel-art sub-app, which is
exactly where that feature discovers itself.

**The real decision is not the UI, it is the bundle.** The current wasm is 152 KB
and it is that small on purpose (`opt-level = "s"`, lto, strip, no `formats`).
Putting clustering and Béziers in the same binary means someone who came to
convert a sprite downloads the photo code.

It does not need solving now, but it **must be left decidable**: add a `photo`
feature gating the new modules and enum variants from the start. It costs nothing
today and allows building two `pkg/` directories with `wasm-pack --features` the
day we measure. Rule of thumb: under ~50 KB of growth, one bundle; over that,
split. What we do not want is to discover it cannot be split.

## 4. Phase 0: the golden file test

### Why

The refactor preserves behaviour *by construction*, but there are **four places
where it degrades silently** and none of them break the current tests:

1. **`simplify()` moved out of `trace()`.** If the `pixel` fitter forgets to call
   it, the SVG looks identical but emits every collinear vertex and the file
   balloons. Nobody notices by looking.
2. **The JS API.** `docs/app.js:1` imports `convertRgba` and passes it a flat
   options object (`wasm.rs:133-149`). If `Config` becomes nested enums,
   `read_config` must keep accepting those same keys mapped to `Grid + Pixel`.
3. **The `Conversion` getters.** `gridWidth`, `cellWidth`, `offsetX` mean nothing
   in photo mode. Turning them into `Option` to accommodate that changes their
   type in the `.d.ts` and breaks the page. That type stays as it is; photo mode
   gets its own result.
4. **Default drift.** Today they are `tolerance: 12.0`, `alpha_threshold: 128`,
   `remove_checkerboard: true` (`lib.rs:58-72`). Unifying them across modes lets
   photo mode's needs (much higher tolerance) drag them. They must be pinned
   explicitly in `GridOptions::default()`.

### Correction to what was said in session

During the conversation I assumed `examples/sonic-a.svg` and `sonic-b.svg` could
serve as golden files because they were committed. **They are not**: `/examples`
is in `.gitignore` and `git ls-files` lists 23 files, none under `examples/`. The
source PNGs are also 1–5 MB, far too large for fixtures.

The fixtures are instead generated **inside the test** from ASCII art, in the
style of `tests/background.rs`. Benefits: no binaries in the repo, deterministic,
and exact control over what each case exercises. Because they use
`convert_rgba()` (raw RGBA buffer) there is no need for the `formats` feature or
for adding `image` to dev-dependencies — and it exercises the same path the web
app uses.

### A golden that never fires covers nothing

Every case **must assert that its feature actually engaged** (`out.cell.0 == 7.0`,
`out.checkerboard.is_some()`, `out.background.is_some()`). A fixture that never
reaches the code it claims to cover passes green forever.

### `tests/golden.rs`

Test names and code comments stay in Spanish to match the rest of `tests/`; only
these session notes are in English.

```rust
//! Instantánea del camino de pixel art: misma entrada, mismo SVG byte a byte.
//!
//! Es la red de seguridad del refactor a dos ejes (segmentación × ajuste): el
//! camino `Grid + Pixel` tiene que seguir dando exactamente lo de hoy.
//!
//! Para regenerar los ficheros tras un cambio intencionado:
//!
//! ```sh
//! UPDATE_GOLDEN=1 cargo test --test golden
//! ```
//!
//! y **mirar el diff** antes de commitearlo.

use std::path::{Path, PathBuf};

use px2svg::{Config, Conversion, Grouping};

fn golden_dir() -> PathBuf {
    Path::new(env!("CARGO_MANIFEST_DIR")).join("tests/golden")
}

/// Paleta del arte ASCII. Sólo ASCII: las filas se miden en bytes.
fn paint(ch: char) -> Option<[u8; 4]> {
    match ch {
        '#' => Some([20, 30, 40, 255]),    // tinta
        'o' => Some([220, 60, 50, 255]),   // segundo color
        '~' => Some([220, 60, 50, 160]),   // semitransparente -> fill-opacity
        '+' => Some([250, 250, 250, 255]), // fondo liso
        _ => None,                         // '.' transparente
    }
}

/// Rasteriza el arte a `scale`x y devuelve el búfer RGBA que espera la web.
fn raster(rows: &[&str], scale: usize) -> (u32, u32, Vec<u8>) {
    let (cols, lines) = (rows[0].len(), rows.len());
    let (w, h) = (cols * scale, lines * scale);
    let mut buf = vec![0u8; w * h * 4];
    for (y, row) in rows.iter().enumerate() {
        assert_eq!(row.len(), cols, "todas las filas deben medir lo mismo");
        for (x, ch) in row.chars().enumerate() {
            let Some(px) = paint(ch) else { continue };
            for dy in 0..scale {
                let base = ((y * scale + dy) * w + x * scale) * 4;
                for dx in 0..scale {
                    buf[base + dx * 4..base + dx * 4 + 4].copy_from_slice(&px);
                }
            }
        }
    }
    (w as u32, h as u32, buf)
}

fn convert(rows: &[&str], scale: usize, config: &Config) -> Conversion {
    let (w, h, buf) = raster(rows, scale);
    px2svg::convert_rgba(w, h, &buf, config).expect("la conversión no debe fallar")
}

/// Compara contra la instantánea.
///
/// Los metadatos de `Conversion` van en una cabecera de comentario, así que el
/// golden sigue siendo un SVG válido que se puede abrir en el navegador para
/// ver *qué* ha cambiado, no sólo que ha cambiado.
fn check(name: &str, out: &Conversion) {
    let actual = format!(
        "<!-- rejilla {}x{} | celda {:.3}x{:.3} | offset {:.3},{:.3} \
| colores {} | paths {} | subtrazados {} | damero {} | fondo {} -->\n{}",
        out.grid.0,
        out.grid.1,
        out.cell.0,
        out.cell.1,
        out.offset.0,
        out.offset.1,
        out.colors,
        out.paths,
        out.subpaths,
        out.checkerboard
            .map_or(String::from("no"), |c| format!("{:.2}px", c.cell.0)),
        out.background.map_or(String::from("no"), |c| c.to_hex()),
        out.svg,
    );

    let path = golden_dir().join(format!("{name}.svg"));
    if std::env::var_os("UPDATE_GOLDEN").is_some() {
        std::fs::create_dir_all(golden_dir()).unwrap();
        std::fs::write(&path, &actual).unwrap();
        return;
    }

    let expected = std::fs::read_to_string(&path).unwrap_or_else(|e| {
        panic!(
            "no se pudo leer {}: {e}\n\
             genéralo con: UPDATE_GOLDEN=1 cargo test --test golden",
            path.display()
        )
    });
    if actual != expected {
        let dump = path.with_extension("actual.svg");
        std::fs::write(&dump, &actual).ok();
        panic!(
            "«{name}» ha cambiado. Compara:\n  diff {} {}\n\
             Si el cambio es intencionado: UPDATE_GOLDEN=1 cargo test --test golden",
            path.display(),
            dump.display()
        );
    }
}

/// Sprite con todo lo que puede romperse en silencio:
/// hueco interior (`evenodd`), diagonales que sólo se tocan por la esquina
/// (conectividad 8 al agrupar, 4 al trazar: `trace.rs:94` y `trace.rs:138`),
/// tramos rectos largos (delatan un `simplify` perdido) y un tono
/// semitransparente (`fill-opacity`, `svg.rs:115-120`).
const SPRITE: &[&str] = &[
    "..######..",
    ".########.",
    ".##....##.",
    ".########.",
    "..#....#..",
    ".#.#..#.#.",
    "..#....#..",
    "..oooooo..",
    "..o~~~~o..",
    "..oooooo..",
];

/// El mismo sprite sobre un fondo liso con margen, para `remove_background`.
const SOBRE_FONDO: &[&str] = &[
    "++++++++++++++",
    "++++++++++++++",
    "++..######..++",
    "++.########.++",
    "++.##++++##.++",
    "++.########.++",
    "++..#++++#..++",
    "++.#.#++#.#.++",
    "++..#++++#..++",
    "++..oooooo..++",
    "++..o~~~~o..++",
    "++..oooooo..++",
    "++++++++++++++",
    "++++++++++++++",
];

#[test]
fn escala_1_1() {
    let out = convert(SPRITE, 1, &Config::default());
    assert_eq!(out.grid, (10, 10));
    check("escala-1-1", &out);
}

#[test]
fn rejilla_detectada() {
    let out = convert(SPRITE, 7, &Config::default());
    assert_eq!(out.cell.0, 7.0, "la detección de rejilla debe enganchar");
    assert_eq!(out.cell.1, 7.0);
    assert_eq!(out.grid, (10, 10), "debe reducir a los píxeles lógicos");
    check("rejilla-detectada", &out);
}

#[test]
fn un_path_por_color() {
    let config = Config {
        grouping: Grouping::Color,
        ..Config::default()
    };
    let out = convert(SPRITE, 1, &config);
    assert_eq!(out.paths, out.colors, "un path por color, sin <g>");
    check("un-path-por-color", &out);
}

#[test]
fn fondo_retirado_y_recortado() {
    let config = Config {
        remove_background: true,
        ..Config::default()
    };
    let out = convert(SOBRE_FONDO, 1, &config);
    assert!(out.background.is_some(), "debe encontrar el fondo liso");
    assert_eq!(out.grid, (10, 10), "y recortar el margen");
    check("fondo-retirado", &out);
}

/// Los defaults del camino de pixel art no se mueven cuando `Config` se parta
/// en `Segmentation` / `Fit`: las necesidades del modo foto no deben
/// arrastrarlos (punto 4 de la lista de degradación silenciosa).
#[test]
fn los_defaults_no_derivan() {
    let d = Config::default();
    assert_eq!(d.scale, None);
    assert_eq!(d.offset, None);
    assert_eq!(d.tolerance, 12.0);
    assert_eq!(d.alpha_threshold, 128);
    assert_eq!(d.pixel_size, None);
    assert_eq!(d.background, None);
    assert_eq!(d.grouping, Grouping::Region);
    assert!(d.remove_checkerboard);
    assert!(!d.remove_background);
}
```
