## Phase 1 — the `Region` IR

Nothing else can start until this exists, and one decision inside it determines
whether phase 4 works at all.

### The half-edge decision

If `Region` carries independent closed loops, every boundary shared by two
regions gets fitted twice — with different results — and a gap opens between
them. Stacking (drawing regions on top of each other, VTracer's default) hides
it; sharing the boundary removes it. Sharing is the better answer and it has to
be designed in now, because it changes the type:

```rust
/// Un tramo de frontera entre dos caras. `right` es `None` en el borde exterior.
pub struct HalfEdge {
    pub points: Vec<Point>,   // polilínea densa, sin simplificar
    pub left: RegionId,
    pub right: Option<RegionId>,
}

pub struct Region {
    pub color: Rgba,
    pub area: usize,
    /// Anillos como secuencias orientadas de tramos; el primero es el exterior.
    pub rings: Vec<Vec<(EdgeId, bool)>>,  // bool = recorrido al revés
}
```

The fitter then runs **once per `HalfEdge`** and both faces reference the same
fitted geometry. Speckle filtering (phase 3) also needs `right` to know which
neighbour to merge a tiny region into, so this pays for itself twice.

### The rest of phase 1

- Introduce `Segmentation` / `Fit` enums and the `Config` shape from the plan.
- Move `simplify()` out of `trace()` (`trace.rs:81-83`) into the `pixel` fitter.
  `polygon` and `spline` need the dense polyline.
- `convert()`, `convert_rgba()`, `convert_image()` keep their exact signatures as
  wrappers over `Grid + Pixel`.
- Pin the pixel-art defaults in `GridOptions::default()` so photo mode's needs
  cannot drag them.

**Acceptance:** `cargo test` green with **no snapshot regenerated**. If a golden
changes, phase 1 has changed behaviour and is wrong.

## Phase 3 — `cluster` segmentation

The first genuinely new algorithm. Target: a 4 Mpx photo in a couple of seconds
in wasm.

### Clustering by runs, not by pixel

A per-pixel flood fill over 4 million pixels is millions of stack pushes with no
locality. Scan each row into **runs** of near-equal colour first, then merge runs
between adjacent rows with union-find. A photo collapses to roughly 20× fewer
runs than pixels, and the merge step is then cheap.

```
for each row:
    cut into runs where distance(prev, cur) > threshold
for each pair of vertically adjacent runs that overlap in x:
    if colours are within threshold: union(a, b)
```

### Colour handling

- **Quantise before clustering**, not after: truncating to N significant bits per
  channel (VTracer's `color_precision`) is O(1) per pixel and makes the run
  boundaries stable. 5 bits is a good default.
- The existing `Rgba::distance` is a weighted-RGB approximation. Good enough for
  pixel-art compression noise, poor for photo clustering — greens and blues at
  equal numeric distance are not equally different to the eye. **Convert to Oklab
  for this path** (~30 lines, no dependency) and keep the RGB distance for the
  grid path so its goldens do not move.
- Optional fixed palette and `max_colors`, as VTracer has. Cheap once clustering
  exists, and genuinely useful for people matching a brand palette.

### Speckle filtering and banding

- **`filter_speckle`**: after clustering, any region under N pixels merges into
  its largest neighbour. Needs the `right` field of `HalfEdge`. Without this a
  photo produces tens of thousands of paths and the SVG is bigger than the PNG.
- **`gradient_step`**: a vector format has no cheap per-region gradient, so a
  smooth ramp has to become discrete bands. Quantising the ramp deliberately
  looks better than whatever the clusterer would do with it unaided.

### Also in this phase

- Extend `background.rs` with a tolerance; it compares exact colours today
  (`background.rs:26`), which never matches on a photo.
- Add the `photo` cargo feature gating these modules, so the wasm bundle can be
  split later without restructuring.

## Phase 4 — the `polygon` and `spline` fitters

### `polygon`

Ramer–Douglas–Peucker over each half-edge chain, tolerance in logical pixels.
Nearly free once the IR exists, and a genuinely useful middle ground: flat-shaded
art vectorises better as polygons than as splines.

### `spline`

The real mathematics, roughly potrace's pipeline:

1. **Corner detection.** Walk the dense polyline, measure turning angle over a
   window, mark anything above a threshold as a corner. Corners split the chain
   into segments that are fitted independently — otherwise a sharp corner gets
   rounded off and the drawing goes soft.
2. **Tangent estimation** at each segment end, from the neighbouring points.
3. **Least-squares cubic fit** (Schneider's algorithm): fit one cubic Bézier to
   the segment, measure maximum deviation, and if it exceeds the tolerance split
   at the worst point and recurse.
4. **Emit** `C` commands. `path_data()` in `svg.rs:150-163` only knows `h`/`v`
   today and needs a curve-aware sibling.

Both fitters run **once per half-edge**, and both faces reuse the result. That is
the whole answer to the seam problem — no stacking needed, no hairlines.

### Output tuning

`path_precision` (decimal places) and coordinate quantisation. The `h`/`v`
shorthand already in `path_data` is the same instinct; curves want the same care.

## CI/CD: `build.yml` and `release.yml`

`pages.yml` becomes two workflows.

### `build.yml` — every push to `main`

```yaml
on:
  push: { branches: [main] }
  workflow_dispatch:
  workflow_call:        # para que release.yml lo reutilice
    inputs:
      ref: { type: string, required: false }
```

Steps: toolchain from `rust-toolchain.toml` → cache → `cargo fmt --check` →
`cargo clippy --all-targets` → `cargo test` (debug, overflow checks on) →
`cargo test --release` → `wasm-pack build` → deploy Pages.

Three things to get right:

- **`workflow_call` needs a `ref` input.** A reusable workflow checks out the
  default ref, so when release.yml calls it *after* pushing a version bump, it
  would build the commit before the bump. Pass the ref explicitly.
- **Permissions do not inherit upward.** `pages: write` and `id-token: write`
  must be declared in the caller as well, or the deploy step fails only when run
  from release.yml — the worst kind of failure to discover.
- **The bump commit retriggers `on: push`.** Either accept the duplicate run or
  guard it, e.g. `if: !startsWith(github.event.head_commit.message, 'release:')`.

### `release.yml` — on demand

```yaml
on:
  workflow_dispatch:
    inputs:
      level:
        type: choice
        options: [patch, minor, major]
```

It cannot be a single job: `jobs.<id>.uses` runs a whole reusable workflow and
cannot share a job with ordinary steps. Three jobs:

1. **`bump`** — compute the new version from `level`, write it to `Cargo.toml`
   and `Cargo.lock`, commit as `release: vX.Y.Z`, tag, push. Outputs the version
   and the commit sha.
2. **`build`** — `uses: ./.github/workflows/build.yml` with `ref` set to that
   sha. Needs `bump`.
3. **`publish`** — matrix build of the CLI binaries, then create the release and
   attach them. Needs `build`.

Binary matrix, one artifact per target:

| Runner | Target |
| --- | --- |
| `macos-latest` | `aarch64-apple-darwin` |
| `macos-13` | `x86_64-apple-darwin` |
| `ubuntu-latest` | `x86_64-unknown-linux-gnu` |
| `ubuntu-24.04-arm` | `aarch64-unknown-linux-gnu` |
| `windows-latest` | `x86_64-pc-windows-msvc` |

Worth attaching the wasm package too — it is the whole web build and someone may
want to embed it.

### Two things this surfaces

- **Release targets do not belong in `rust-toolchain.toml`.** That file pins the
  *development* toolchain; adding five cross-compilation targets to it would make
  every local `rustup` install download all of them. Add them per-matrix-entry
  with `rustup target add` in the release job instead.
- **There is no LICENSE file, and `Cargo.toml` has no `license` field.**
  wasm-pack already warns about it. Shipping binaries in a public release without
  a licence is a real gap, and the missing field would also block
  `cargo publish` if that ever comes up.

## Leftovers not tied to a phase

- **Corpus in CI.** The three PNGs are not in the repo and weigh 9 MB. Until they
  are reachable from a clean clone, six tests pass without checking anything.
  `REQUIRE_CORPUS=1` is wired and waiting. Options: a release asset fetched in
  CI, a separate fixtures repo, or Git LFS.
- **`.d.ts` guard.** Nothing catches a breaking change to the JS API. Build the
  wasm in CI and diff `docs/pkg/img2svg.d.ts` against a committed copy.
- **Homebrew Rust shadows rustup locally.** `rust-toolchain.toml` is only honoured
  by rustup's shims, and `/opt/homebrew/bin/rustc` comes first on `PATH`, so it
  ignores the file entirely. Fix on the machine, not in the repo:
  `brew uninstall rust`, or put `$HOME/.cargo/bin` ahead of Homebrew in the
  shell profile.
- **`checker.rs` has no golden with a real checkerboard from a clean clone.** It
  is covered by `corpus-damero`, which is exactly the test that skips without
  the corpus. Same fix as above.

## Order, and what each phase must not break

```
Infra    docs/ -> web/, docs/ for prose   ← independent, do it first: it moves
                                            paths that everything else edits
Infra    build.yml + release.yml          ← after the move, same paths
Phase 1  Region IR + Segmentation/Fit     ← blocks 2, 3, 4
Phase 2  CLI + drop the name px2svg       ← independent of 3 and 4
Phase 3  cluster segmentation             ← blocks the curves engine
Phase 4  polygon and spline fitters       ← needs 1 and 3
Phase 5  curves in the web, bundles       ← needs 3 and 4
```

The two infrastructure items go first on purpose. Both rewrite paths and
workflow files that every later phase would otherwise touch again, and neither
depends on any of the Rust work. Doing the `web/` move *after* phase 2 would mean
renaming things twice.

Every phase runs against the same rule: **the pixel-art snapshots do not move.**
Phases 3 and 4 add new goldens of their own (a photo through `cluster + spline`,
and a sprite through `grid + spline` — the combination nobody else can do), but
none of the 11 existing ones may change without a deliberate, reviewed reason.
